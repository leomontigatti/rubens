# Validation

What a session runs before it commits, and which tool owns which concern. CI is
the merge gate; a session's job is to catch its own mistakes cheaply, not to
reproduce CI.

## Before committing

```sh
pnpm check                      # formatting check, lint and type check (`vp check`)
pnpm test:unit <path>...        # the unit test files your change touches
pnpm test:workers <path>...     # the Workers test files your change touches: the organization object, the request-to-caller step
pnpm test:e2e                   # the whole browser suite: CI's `e2e` job runs it (§ Heavy)
python3 -I ~/.agents/workflow/skills/domain-modeling/scripts/anchors.py   # every ADR anchor and glossary term is still in the code
```

Run this once, after your edits. Do not run `pnpm test` in a session: it runs
both suites in series, and CI runs them again. `pnpm check` prints only the
failures, each at its file and line; fix them and rerun it. Never pipe its output
into `tail` or `head`, which hides the failure.

Run `pnpm typecheck` and `pnpm build` one after the other, never in parallel.

## Heavy

`pnpm test:e2e` runs in CI instead of the session: the `e2e` job of
`.github/workflows/ci.yml`, by the `implement` skill's `HEAVY.md`, while the rest
of § Before committing runs here. When the branch's whole diff against `main`
(`origin/main...HEAD`, not the last commit) is only Markdown and `docs/`, the job
skips its steps and still concludes `success`: its `classify the diff` step
prints "the browser suite skips". So a merge from `main` into a docs-only branch
still skips, and a docs-only commit on a code branch still runs the suite. When
the job did not run, the whole browser suite runs here, as `HEAVY.md`'s fallback
says.

## The assistant's evaluation

`pnpm eval:assistant`, `pnpm eval:voice` and `pnpm eval:template-review` are paid runs on
provider keys a session's machine does not hold
([tests/evals/assistant/README.md](../../tests/evals/assistant/README.md)): the maintainer
runs them. A session's part is to say which run its change calls for and hand it over.

A change calls for a run when it changes what one of them measures:

| The change                                                                                                                                                                            | The run it calls for                                             |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| What the assistant's model reads in a turn: the system prompt, a tool's schema or description, a note added to the turn (`src/lib/assistant.ts`), or what a tool returns to the model | `pnpm eval:assistant <the assistant's model> --repeat 3`         |
| The template review's prompt or schema (`src/lib/template-review.ts`)                                                                                                                 | `pnpm eval:template-review`                                      |
| The transcription model (`transcriptionModelId`)                                                                                                                                      | `pnpm eval:voice --assistant <the assistant's model> --repeat 2` |
| The assistant's model (`assistantModelId`)                                                                                                                                            | all three, on the new model                                      |

The session still makes the set match the change: a tool that returns something new answers
the same way in `fake-object.ts` and `world.ts`, and a new behaviour gets its case in
`cases.ts`. Then it hands the run over in three places, each naming the command and what
changed in what the model reads:

- **The PR body** opens with it, as the thing the maintainer must do.
- **The issue** the PR closes is marked as work for a human
  ([issue-tracker.md](./issue-tracker.md#labels)) once the PR is ready, with the same text as
  a comment.
- **The final report** lists it first, among the checks the session could not run.

## As you go

Each time a slice goes green, check that slice alone:

```sh
pnpm typecheck                  # types only, faster than `pnpm check`
pnpm test:unit <path>           # or `pnpm test:workers <path>`: the one test file of the slice
```

## Hooks inside the session

The project's agent hooks ([agent-configuration.md](./agent-configuration.md#session-hooks))
run only in the harnesses that wire them, Claude Code and Codex. A Capy thread runs none
of them, so there the session does their work itself: format each file it writes with
`pnpm exec vp fmt <file>...`, run `pnpm install --frozen-lockfile` when `pnpm-lock.yaml`
changed, and before it ends run `pnpm check`, `pnpm check:fallow` and `pnpm check:dupes`,
reading the last two by exit code as [fallow.md](./fallow.md) says. Like the `Stop` hook, it
runs them only when the working tree changed a TypeScript or JavaScript file, a
`package.json` or a `tsconfig`, and skips the two fallow gates on a `prototype/*` branch.

Where they do run, they run three of these checks for you:

- every file the agent writes is formatted;
- the end of a turn is blocked while `pnpm check`'s lint or type check is red, or
  `pnpm check:fallow` or `pnpm check:dupes` fails, by exit code as [fallow.md](./fallow.md)
  reads it, so a complexity finding or duplication over the threshold lands on the turn
  that wrote it rather than at commit;
- before those, the end of a turn is blocked with one line when `pnpm-lock.yaml` is
  newer than the installed dependencies: run `pnpm install --frozen-lockfile`, not a
  lint fix.

The shared workflow's hooks, installed at user level and run in the same harnesses, add one
more: `pkill -f` is refused, in favour of `pnpm dev:stop`
([verification.md](./verification.md#cleanup)).

The `Stop` hook is a backstop, not a substitute for running `pnpm check` yourself.
`SKIP_STOP_CHECKS=1` turns it off for local work, never to get a red branch
committed.

## Browser checks

Anything the dev server renders is checked in a browser, following
[verification.md](./verification.md). A browser check is not a validation command,
and CI does not run it: it proves one change once and leaves no test behind. What
CI does run in a browser is the suite in `tests/e2e/` (`pnpm test:e2e`), which
covers the smoke pass, the booking flows and the races already fixed.

## Why not `pnpm test`

`pnpm test` is `test:unit && test:workers`, in series, and CI runs both on every PR
that changes code. A session runs the files it touched and leaves the rest to CI. Run
the whole Workers suite only when the change reaches every object test, such as the
schema, a migration or `organization.test-support.ts`, and say why in the report.
